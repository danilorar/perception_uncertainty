How HiDrive AEB was wired into Studio

Note (2026-10-20): this page describes the retired esmini 2.40 integration. The controller has been ported to the esmini 3.8.1 API; its source lives in AEB Controler (esmini 3.8.1) and hidrive/build.py compiles it into the isolated esmini-hidrive-v3.8.1. See hidrive/README.md and hidrive/MIGRATE-3.8.1.zh.md for the current setup; line links below point to the old 2.40 tree.

There are two layers. First, the controller is compiled into a separate esmini 2.40 executable. Then Studio calls that executable to run the teacher's scenarios and converts its output into Studio's existing file format. The controller source was never modified and was never read by an AI.

Click a file or function name to open it in VS Code on this computer at that line. Teammates: change the path to the project folder on your own machine. The esmini 2.40 files exist only after running hidrive/build.py once.

The esmini 3.8.1 library Studio normally uses does not contain this controller, so HiDrive takes a separate path. Studio does not step the simulation itself. It hands the whole scenario to the 2.40 executable, lets it run to the end, and then reads the results.

LAYER 1 · BUILD

Compiling the controller into esmini 2.40

The controller is written against the esmini 2.x API and does not compile inside 3.8.1. A separate copy of esmini v2.40.0 (commit c5f50c7) therefore lives in esmini-lab/runtime/esmini-hidrive-v2.40.0/.

For esmini to recognise a new controller, three places in its public source have to change. Two small edits to CMakeLists.txt also stop it from downloading test data and external packages that are not needed.

How the build works

simulation-studio/hidrive/build.py does all of the above in one command:

  1. If the esmini 2.40 source is missing, it downloads v2.40.0 from GitHub.
  2. It applies the public-file edits in the ENGINE_EDITS list. Edits already present are skipped, so running it again is safe.
  3. It copies the OSG / OSI / SUMO packages from the project's existing esmini 3.8.1 full install instead of downloading them.
  4. It copies the two controller files with shutil.copy2. They are copied, never opened.
  5. It configures with CMake, builds the esmini target (Release, x64) and copies the exe to bin/esmini.exe.
cmake -S esmini-hidrive-v2.40.0 -B build -A x64 -DUSE_OSG=ON -DUSE_OSI=ON -DUSE_SUMO=ON \
      -DUSE_GTEST=OFF -DDOWNLOAD_EXTERNALS=OFF ...
cmake --build build --config Release --target esmini

Compiler output goes only to esmini-lab/evidence/hidrive-build.log and is not printed to the terminal, because compiler errors may quote the controller source. An incremental build takes about 6 seconds; the first full build takes a few minutes.

The key problem: it crashes without a viewer

After the build succeeded, running a scenario with the usual no-window flag --headless made the program exit at about 0.05 s of simulation time, with nothing in the log. Three time steps (0.05 / 0.01 / 0.001 s) all crashed at the same simulation time, while running with a visible window completed the full 10 s. The conclusion: the controller uses the viewer object and dereferences a null pointer when there is no viewer.

The fix comes from esmini 2.40's public source:

  • playerbase.cpp: a viewer is created whenever --window is on the command line.
  • InitTraits() in viewer.cpp: if --headless is also set, it sets traits->pbuffer = true, which renders off-screen in GPU memory instead of opening a desktop window.

Using both flags together gives the controller the viewer it needs, and no window appears on the desktop. Neither the controller nor the engine had to change.

esmini.exe --osc scene.xosc --headless --window 0 0 320 180 ...
LAYER 2 · RUN

How Studio calls it

The core is run_hidrive() in the new file simulation-studio/hidrive_runner.py. Each run goes through these steps in order:

  1. check_build(): checks that bin/esmini.exe exists, and compares the size and modification time of the files in AEB Controler/ with the copies used for the build. If they differ, it stops and asks for a rebuild.
  2. build_hidrive_scene(): copies the teacher's scenario into the run folder and only turns the road and vehicle-catalog paths into absolute paths. HiDriveController and its parameters stay as they are.
  3. Launches the 2.40 executable with --headless --window (above), Studio's time step via --fixed_timestep, collision detection via --collision, and two outputs: --csv_logger and a log file.
  4. read_esmini_csv(): reads esmini's CSV to get each vehicle's position, speed, heading, bounding box and collision partners at every frame.
  5. read_log_values(): reads the LOG_VALUE:AEB_active and LOG_VALUE:Acceleration lines the controller writes to the log, used as "AEB trigger" and "commanded acceleration".
  6. Converts everything into Studio's standard files: ego.csv, truth.csv, observations.csv, metrics.csv. Minimum gap and TTC are computed from true positions. Output is cut at the first collision frame, the same rule as the native ACC.
  7. Hands over to the existing finish_run(), which produces the charts (plots.py) and the MP4 (video.py replays truth.csv in esmini 3.8.1).

Daily use and when to rebuild

Running experiments

No build needed. In Studio, set the controller to HiDrive AEB and click "Run new simulation".

Controller files changed

Run this once from the simulation-studio folder:

.venv\Scripts\python.exe hidrive\build.py

First time on a new machine

Install the full esmini 3.8.1 and the Visual Studio C++ toolchain first, then run the same build command. It downloads the 2.40 source automatically.

Current limitations

  • Perception error cannot be injected. The controller uses its own internal perception, so Studio's OU range error never reaches it, and only ideal detection is allowed with HiDrive. Adding error requires knowing which interface the controller reads the lead-vehicle distance from.
  • "AEB trigger" and "acceleration" come from values the controller writes to the log. Position, speed and collisions come from esmini's true state.
  • The engine is esmini 2.40, not the 3.8.1 used by the rest of Studio. Video replay still uses 3.8.1.
  • The small saw-tooth at the start of the ego speed curve comes from the coordinate precision (0.01 m) of the teacher's trajectory file, not from the controller.
Results on the three teacher scenarios: 1549178 and 1554254 have no collision, with AEB triggering at 3.31 s and 3.20 s. In 1554431 AEB triggers at 3.23 s and the ego hits the lead vehicle at 5.49 s at 34 km/h.
